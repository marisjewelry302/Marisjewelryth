Data model and API flow

Recommended backend boundary: public form posts to a server-only API, which writes Supabase with the service role key and sends both emails through the existing Resend helper style.

Client

/contact-order/SR000

Validates required fields, email format, phone characters, and optional specs before submit.

Server API

POST /api/custom-order-requests

Re-validates everything server-side and never accepts customer_id from the browser.

Supabase

customers

Find by normalized email, fallback to phone, then create or update a guest/lead customer record.

Supabase

custom_order_requests

Stores the request, optional specs, status pending, and nullable customer_id link.

Submit JSON Service role only Lead link Pending request
Email 1

Customer confirmation

Thanks the customer, repeats product code and selected specs, and says the team will contact back.

Email 2

Admin notification

Sends all customer details and specs to the Maris internal order inbox.

Response

Success state

Returns request id/status only. No Supabase keys, no internal customer metadata, no order checkout behavior.

Failure

Helpful error

If DB or email env is missing, show a submit error and keep the filled form intact.

Customer link rule

Use the existing `customers` table, but the migration/design will explicitly verify the active customer column shape. The app code currently expects `full_name`, while the oldest base migration shows `name`, so this feature should include compatibility checks instead of assuming silently.
